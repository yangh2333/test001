# PMO 平台推广与运营章程

版本：v1.0　日期：2026-11-01　依据：F 组 10 题答案 + A3（服务型 + 交付责任制）+ D5/D10（一线体验）

---

## 0. 定位声明（先讲清楚 PMO 是干什么的）

> **PMO 是服务型组织，但对交付数据负责。**

- **服务型**：PMO 提供流程、模板、工具和看板，不代替业务部门做业务决策，不以行政手段强制卡流程；
- **交付责任制**：PMO 对**平台中数据的真实性、及时性与完整性**负责，对项目里程碑是否达成**不承担业务责任**；
- 一句话区分：**Gate 由业务方自己承诺，PMO 负责把承诺记下来、盯住、暴露出来。**

这一条决定了后面所有规则——门禁是"承诺制 + 记账"而不是"审批卡口"，考核是"数据质量"而不是"项目成败"。

## 1. 组织与职责（F8）

| 角色 | 编制 | 职责 | 归属 |
| --- | --- | --- | --- |
| PMO 运营小组 | **常设 2–3 人** | 模板治理、字典维护、数据稽核、运营月报、答疑 | PMO |
| 密级管理员 | 1 人（兼） | 密级设定与变更的审批、越权扫描复核 | PMO |
| 种子用户 | 每个 BU 2 名 | 一线答疑、需求收集、新功能内测 | 各 BU |
| IT 技术支持 | 按需 | 服务器、数据库、网络、账号同步、出网审批 | IT |
| 开发方 | 2–3 人 | 迭代交付、缺陷修复、技术支持 | 内部/外部 |

**运营小组不得空缺**——G 组风险中"无专职运营致数据质量滑坡"已被勾选，这是发生概率最高的一条。

## 2. 试点与推广（F1/F2/F3 + D-6）

### 2.1 试点范围

- **试点 BU：芯片 BU + 系统硬件 BU**（D-6 确认）
- 试点期：**4 个月**（F2）
- 覆盖：试点 BU 内**全部在建项目**，不留例外（否则数据不完整）

### 2.2 试点期数据规则

- 试点期所有数据标记 **"待校准"**，正式基线在首个 Gate 复核后转正式；
- 试点期**允许补录**，但补录需注明"回填"并计入数据质量指标；
- 试点期不计入里程碑按期率考核。

### 2.3 转正与收敛

| 时点 | 动作 |
| --- | --- |
| 试点第 4 月 | 验收：周报人工工时下降 ≥ 60%、跨部门请求 100% 走工单、BU 内项目 100% 上线 |
| 转正后第 1 个月 | **新旧并行期**：Excel 与平台双轨，允许过渡 |
| 并行期结束 | **由分管副总发文**，明确：部门周报、月度汇报材料**一律以平台出数为准**，不再接受 Excel 版本 |

> F3 的关键在于"谁来下令"。并行期不能自然收敛，必须有人在会上说一句"下个月起不收 Excel 了"，否则会永远双轨下去。

### 2.4 培训（F7）

- 每个 BU 培养 **2 名种子用户**，上线前完成 **2 小时实操培训**，覆盖率目标 100%；
- 培训内容分三档：PM（4 小时，含模板与 Gate）、成员（1 小时，含领任务与填报）、主管（2 小时，含资源与看板）；
- 答疑通道：企微群 + 每周固定 1 小时"坐班"时间。

## 3. 数据与流程治理

### 3.1 数据质量规则（F6）

| 指标 | 目标 | 考核对象 | 频率 |
| --- | --- | --- | --- |
| 项目必填字段完整率 | ≥ 95% | PM | 月度运营月报 |
| 周报及时率（周五 18:00 前） | ≥ 90% | PM + 部门 | 月度 |
| 工时填报率 | ≥ 85% | 部门 | 月度 |
| 任务状态更新及时率（超 3 天未更新记为滞后） | ≥ 90% | 任务 owner | 月度 |
| 风险复审及时率 | ≥ 90% | 风险 owner | 月度 |
| 评审问题闭环率 | ≥ 85% | 评审主持人 | 季度 |

**考核落点**：纳入部门与 PM 的绩效考核，但**只考核数据质量，不考核项目成败**。

### 3.2 工时数据使用红线（D9 + G 组勾选）

> **工时数据仅用于成本核算与负载分析，不得用于个人绩效问责。**

- 个人明细仅本人与直属主管可见；部门层面为**匿名聚合**；
- 报表不提供"个人完成率排行""加班时长排行"类视图；
- 违反此条需 PMO 负责人书面批准，并在全员范围内说明用途。

理由很直接：一旦工时与绩效挂钩，填报立即失真，M7 与整个成本口径就废了。这条要写进制度，不能只写在文档里。

### 3.3 模板治理（F10）

| 事项 | 规则 |
| --- | --- |
| 模板与 Gate Checklist 维护权 | **PMO 统一负责** |
| 常规修改（字段、说明、排序） | PMO 审批后生效 |
| 重大修改（增删阶段、改 Gate 判定标准） | PMO 负责人 + 领域主管会签 |
| 争议裁决 | **总裁会**（F10 回决，原 CTO 办公室已上调） |
| 模板裁剪 | 允许裁剪，但核心 Gate 与关键字段**不可裁剪**；裁剪项需 PMO 审批并留痕 |
| 版本化 | 模板升级不影响历史项目（历史项目沿用旧版本） |

### 3.4 密级管理（A2）

- 密级为立项**必填项**（公开/内部/机密/绝密）；
- 创建后变更需**双人审批**（密级管理员 + 项目负责人）；
- 每周跑一次越权扫描（密级 × 数据域 × 项目成员交叉校验）；
- 机密及以上项目禁止外部账号访问、禁止导出。

## 4. 协同与裁决规则（F5 + D5）

| 场景 | 规则 |
| --- | --- |
| 跨部门资源/支持请求 | **必须走协同工单**，禁止口头拉人（D5 首要痛点） |
| 工单响应 SLA | 默认 **1 个工作日**内响应 |
| 升级机制 | 超 48h 未响应 → 自动升级至对方部门主管；72h 未决 → 升级分管副总；**3 个工作日内必须出结论** |
| 责任人唯一化 | 每个任务/工单**有且仅有一个 accountable owner**，杜绝"两个人负责=没人负责" |
| 人责地图 | 平台提供"谁能决定/谁能执行/需咨询谁"检索，解决"找不到责任人" |

**文化提示**：工单化的真正价值是**把人际成本转给系统**——D5 提到"协调比较复杂且得罪人"，用系统派单后，"催办"是系统在做，不是某个 PM 在做。

## 5. 需求与版本节奏（F9）

| 项 | 规则 |
| --- | --- |
| 迭代周期 | **双周迭代** |
| 大版本 | **季度** |
| 需求入口 | 企微群 / 种子用户 / 运营月报，统一进需求池 |
| 优先级 | PMO 与开发方联合排序（业务价值 × 影响面 ÷ 工作量） |
| 紧急需求 | 仅 P0 故障可插队，需 PMO 负责人批准 |
| 需求拒绝机制 | 明确告知"不做"及理由，避免无限期待 |

## 6. 变更与例外（A3 承诺制）

| 情形 | 处理方式 |
| --- | --- |
| Gate 未通过但需继续推进 | 填写**风险接受说明**（原因 + 影响 + 缓解措施），进入承诺台账，系统持续红色告警并抄送 PM 主管与 PMO |
| 高危 Gate（Tapeout / MP 放行等） | 恢复强制校验，Checklist 未完成不放行 |
| 绕过门禁 | 允许，但必须留痕，且季度运营月报披露 |
| 例外累积过多 | 某 BU 季度例外 > 5 次，触发 PMO 与 BU 负责人专项复盘 |

**立场**：服务型不等于无原则放行。例外可以走，但必须记账、必须可见——数据真实比流程严整更重要。

## 7. 例会与运营节奏

| 频率 | 会议 | 输入 | 输出 |
| --- | --- | --- | --- |
| 每周 | 项目周会 | 平台自动生成的周报草稿 | PM 补充后发布，三级汇聚 |
| 每周 | 运营小组例会 | 数据质量指标 | 催办清单 |
| 每月 | PMO 运营月报 | 6 项数据质量指标 + 例外台账 | 通报至各部门主管 |
| 每月 | 经营会 | 高管驾驶舱（节点/阻塞/待决策） | 决策事项闭环 |
| 每季度 | 平台复盘会 | 需求池、满意度、故障 | 下季度路线调整 |

**高管参与硬约束**（G 组已勾选"高管只看数不操作"风险）：
- 经营会材料**必须由平台出具**；
- 待决策事项推送到高管企微卡片，支持**一键批准/驳回**；
- 每季度公示"高管平台在线操作次数"——不是考核，是示范。

## 8. 违规与退出

| 违规 | 处理 |
| --- | --- |
| 长期不填报（连续 4 周） | 通报至部门主管 |
| 私下维护 Excel 双轨 | 部门主管约谈；运营月报点名 |
| 越权访问 / 导出涉密数据 | 立即冻结账号，安全审计介入 |
| 工时数据用于绩效问责 | PMO 负责人书面说明，情节严重的上报 |

## 9. 章程生效与修订

- 本章程由 PMO 负责人签发，**试点启动时生效**；
- 修订需 PMO 运营小组提出，PMO 负责人审批；涉及考核条款的需分管副总批准；
- 每半年复盘一次，与平台季度大版本同步更新。
